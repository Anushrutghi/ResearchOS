# v4 — ResearchOS v0.5 Experiment and Reproducibility Engine

**Status: Complete**

## Scope

Implement experiment records and isolated execution, dataset import/validation/versioning, Python and notebook workflows, resource monitoring, approved dependency handling, statistical analysis, task-appropriate ML baselines/metrics, experiment tracking, actual-data visualizations, logs, and reproducibility metadata.

## Acceptance checks

- No research-generated code runs directly on the host; sandbox limits and credential/network isolation are enforced.
- Dataset originals are unchanged and every transformation is recorded.
- Results come only from execution records; failures remain failed and proposed results remain unavailable.
- Configuration, seeds, environment, inputs, outputs, and logs support reruns.

## Implemented so far

Generated research code, notebooks, datasets, dependency metadata, and imported results are untrusted. The runner must assume code may attempt host-file access, network access, credential discovery, process creation, resource exhaustion, output flooding, and forged result claims. Dataset files are mounted read-only; run outputs are captured separately and bounded. The run record must distinguish requested configuration from observed execution results, and a failed or unavailable sandbox cannot produce a successful result record.

- Added content-addressed CSV/JSON dataset intake with row/header validation, preserved originals, SHA-256 verification, import events, and lineage records for researcher-described transformed outputs.
- Added bounded column profiling with heuristic type, missing-value, and numeric-range summaries. Profiling samples the first rows and records whether it covered the full dataset; it is not a verified schema.
- Changed JSON dataset validation to decode row objects incrementally rather than materializing the full row list. Duplicate object keys and non-finite numbers, including nested values, are rejected; CSV and JSON intake enforce a 10,000,000-cell ceiling alongside existing byte, row, and column limits.
- Added durable experiment records containing source hash, seed, dataset hashes, requested image/limits, execution output, duration, and explicit failure state. Records are persisted as running before execution; unavailable or failed execution remains failed.
- Added deterministic classification and regression evaluation for researcher-selected prediction columns, including confusion matrix/per-class metrics and simple majority/mean baselines. Evaluation records link to dataset hashes and are explicitly descriptive.
- Added local SVG confusion-matrix and actual-versus-predicted visualizations. Regression charts use a deterministic sample of at most 1,000 points and disclose sampling.
- Added local browser and HTTP routes for dataset import/download, dataset listing, experiment submission, and execution records. Code execution requires an explicit researcher action.
- Added a local JSON image manifest bound to the configured image digest. API and browser requests can include exact dependency pins; unapproved pins are rejected, and run records retain requested pins, the Python version, and manifest hash. The manifest is an operator attestation and does not verify installed packages inside the image; ResearchOS does not install dependencies or enable network access.
- Added periodic Docker CLI CPU/memory sampling while a named container is active. Execution records store sample count and maximum observed CPU/memory with the sampling interval; the UI displays these values and reports unavailable telemetry explicitly. Short peaks between samples can be missed.
- Added a 32 MiB container tmpfs at `/artifacts`. Successful runs can preserve up to 20 flat regular files and 16 MiB total; stored files are read-only, content-hashed, integrity-checked on download, and linked from the experiment record. Symlinks, directories, unsafe names, and excess output are rejected.
- Added Jupyter notebook v4 intake through the browser and API. Up to 200 cells and 2 MiB of notebook JSON are accepted; Python code cells execute sequentially through the exact same sandbox as scripts. Markdown and stored outputs are preserved but never executed or treated as results; IPython magics and shell escapes are rejected. The original notebook hash, code-cell hashes, and normalized executable source are persisted.
- Added a reproducible sandbox image recipe with a digest-pinned Python base and hash-checked dependency lock. Registry publication is required to obtain the digest reference used by the runner. The local manifest remains an operator attestation and is not a package-content verification mechanism.

## Threat model and backend decision

The initial backend is Docker/OCI via the local Docker CLI. A run is permitted only with a locally present image pinned by SHA-256 digest, `--pull=never`, no network, read-only root filesystem and source/data mounts, unprivileged UID, dropped capabilities, no-new-privileges, bounded memory/CPU/PIDs/time/output, and forced container cleanup. No API credentials or host environment are passed into the container. The Docker daemon and pinned image remain trusted components and must be documented as part of the host threat boundary. There is no host-Python fallback. Generated code may still exploit vulnerabilities in the trusted daemon, runtime, kernel, or image.

The Docker daemon and the exact digest-pinned image are trusted components. A live test against `python@sha256:4840d514c583a4d3d8cad3940e68dee6f0f6f3635c12fcd0a3d74c21a5b93a54` verified UID 65534, read-only root/workspace/dataset mounts, blocked outbound networking, Python version, artifact persistence and hash, sampled Docker resource telemetry, and removal after timeout. This is a targeted boundary check, not a general security certification. Sampling can miss brief CPU/memory peaks; the daemon, kernel, and image remain in the trust boundary.
